# 대화로 포트폴리오를 만드는 작업 공간 — 상세 설계

상태: **제안 초안 / 미구현** (2026-11-09). 기준 계약: [ARCHITECTURE-SPINE.md](ARCHITECTURE-SPINE.md). 이 문서의 신규 API와 자료 구조는 목표 계약이며 현재 동작한다는 뜻이 아니다.

## 1. 제품이 해야 하는 일

사용자가 사진·도면·PDF·설명·기존 포트폴리오를 넣고 대화로 방향을 설명한다. 에이전트는 자료의 내용과 권리를 확인하고 이야기와 시각적 구성을 계획한다. 오른쪽 DesignCraft에서 페이지를 보고 직접 고치거나, 대화로 특정 요소와 여러 페이지의 수정을 요청한다. 결과를 비교·검토한 뒤 편집 가능한 원본과 PDF 등 목적에 맞는 결과를 저장한다.

예: 사용자가 “2페이지 조감도를 더 크게 하고 설명을 줄여 줘”라고 하면, 선택 페이지의 **현재** 버전과 조감도 출처를 읽고, 변경안과 영향 범위를 보여 준다. 승인 시 해당 요소만 수정하고 결과를 다시 렌더한다. 다른 요소를 의도치 않게 바꿨거나 도면이 잘리면 차단하거나 승인 요청한다.

## 3. 사용자 흐름과 담당 모듈

| 단계 | 사용자 행동 | 담당 / 결과 |
|---|---|---|
| 시작 | 가입·프로젝트 생성, 목적·분야·매체 선택 | 인증·프로젝트 서비스. 출력 규격은 프로젝트별로 지정 |
| 자료 | 사진·도면·PDF 업로드, 자료 선택 | 자료 저장소 + sourcePrepAgent. 원본 해시·권리·파생 관계 기록 |
| 방향 | 대화로 용도·분량·스타일 설명 | 대화 오케스트레이터 + portfolioAgent. 근거 자산과 생략 이유가 있는 계획·서사 |
| 초안 | 후보 방향 선택, 페이지 생성 | portfolioAgent + 편집기 어댑터. 편집 가능한 문서·미리보기·입력 연결 |
| 함께 편집 | 선택 요소나 페이지를 지정해 변경 요청 | 라이브 상태 스냅샷 → 제안 → 승인 → 편집 연산 → 재조회·미리보기 |
| 검토 | 결과 비교, 차단·경고 확인, 사람 평가 | 게이트 + reviewAgent. 실제 문서/렌더 해시에 묶인 리뷰 |
| 완료 | 저장·PDF 등 내보내기 | 불변 문서 버전 및 출력 manifest. 실제 출력 검증 상태 별도 표시 |

에이전트는 필수로 프로세스를 여러 개 띄우는 개념이 아니다. 분리된 역할과 계약을 우선 유지하고 배포·동시성 요건이 생길 때만 실행 경계를 확장한다. `DiagramAgent`와 `pptAgent`는 별도 선택형 저장소이므로 설치나 실행을 전제하지 않는다.

## 4. 대화 ↔ 편집기 프로토콜

### 읽기: 첫 단계에서 반드시 확보할 상태

브라우저에서 편집기의 `document.snapshot.v1`을 요청하고 사용자의 현재 선택과 페이지 범위를 명시한다. 다음은 **제안 계약**이다.

```json
{
  "schema_version": "document.snapshot.v1",
  "project_id": "p1", "document_id": "d1", "live_revision": "r42",
  "saved_version_id": "v7", "dirty": true,
  "selection": {"page_id": "pg2", "object_ids": ["obj7"]},
  "pages": [{"id": "pg2", "size_mm": [297, 210], "objects": [
    {"id": "obj7", "kind": "image", "bounds_mm": [20, 20, 120, 90], "asset_version_id": "asset-v3"}
  ]}],
  "preview": {"ref": "authorized-preview-ref", "revision": "r42"},
  "capabilities": ["inspect", "preview"], "omissions": ["font_substitution_details"]
}
```

- ID 안정성과 revision 증가 범위(사용자 편집, undo/redo, 저장, 열기)를 어댑터 테스트로 증명한다. 복원 불가·임시 ID면 수정 대상으로 쓰지 않는다.
- 스냅샷은 필요한 페이지·요소만 추출한다. 문서 텍스트와 이미지/미리보기를 모델에 넘길 때 공급자, 범위, 잘림·실패 상태를 기록한다. 스냅샷을 사용자에게 알리지 않고 외부로 전송하지 않는다.
- 디자인 편집 상태는 브라우저 세션의 라이브 문서가 권위다. 백엔드 DB에는 마지막으로 확정된 불변 문서 버전과 관련 이력을 저장한다. 저장되지 않은 상태를 저장된 파일인 양 조회하지 않는다.
- 브리지는 `postMessage` 출처·부모 확인과 request ID를 유지하되, 서버는 별도 사용자 인증 및 프로젝트 권한을 확인한다. 이미지 바이트나 임의 경로를 메시지에 실어 무제한 전달하지 않는다.
- 업로드한 문서와 이미지에 포함된 문구는 신뢰할 수 없는 자료다. 모델이 자료 안의 지시를 사용자 지시나 시스템 권한으로 승격하지 않도록 도구 호출과 자료 접근 범위를 서버에서 검증한다. 모델의 설명만으로 권한·출처·성공 여부를 결정하지 않는다.

### 쓰기: 제안 → 적용 → 재확인

```json
{
  "schema_version": "edit.proposal.v1", "proposal_id": "pr1",
  "project_id": "p1", "document_id": "d1", "base_revision": "r42",
  "operations": [
    {"op": "image.resize", "page_id": "pg2", "object_id": "obj7",
     "bounds_mm": [20, 20, 160, 110], "crop_policy": "preserve"}
  ],
  "source_version_ids": ["asset-v3"], "explanation": "조감도 강조",
  "approval_required": true
}
```

1. 오케스트레이터는 사용자의 의도, 스냅샷, 권한과 capability를 확인해 제안을 생성한다. LLM은 도구 이름·타깃·값을 임의 코드가 아닌 구조화된 데이터로 반환한다.
2. 정책 검증은 지원 연산, 객체 소속, 값의 범위, 원본·권리·크롭 제약, 다른 객체 영향과 revision을 확인한다. 디자인 제안의 텍스트와 출처가 일치하는지도 따로 검증한다.
3. 사용자는 변경 전후 범위와 경고를 보고 적용한다. 이미지 생성·잘라내기 등 고위험 변경은 별도 동의한다.
4. 편집기 내부 단일 쓰기 경계에서 revision 비교와 적용을 하나의 원자적 작업으로 처리한다. 다르면 `REVISION_CONFLICT`: 현재 상태를 다시 읽고 새 제안을 만들며, 이전 제안을 자동으로 덮어쓰지 않는다. 브라우저에서 비교한 뒤 별도 메시지로 적용하는 방식은 중간에 사람 편집이 끼어들 수 있어 불충분하다.
5. 편집기 어댑터가 원자적으로 적용할 수 있는 연산만 실행한다. 불가능한 묶음은 실행 전 거부하거나 안전한 작업 단위로 나눈다. 실패 후 부분 변경 가능성이 있으면 `UNKNOWN_OUTCOME`으로 표시하고 현재 문서를 재조회한다.
6. 프로젝트·문서·편집 세션 범위의 `request_id`와 요청 내용 해시, 결과 ledger로 동일 요청 재전송 시 중복 적용을 막는다. 같은 ID에 다른 내용을 보내면 거부한다. 브라우저가 끊겨 성공 여부가 불확실하면 재실행 전에 편집기 상태와 신뢰할 수 있는 ledger를 확인한다. 영속 receipt가 없다면 재시작 후 정확히 한 번 실행을 보장한다고 주장하지 않는다.
7. 적용 후 새 revision과 실제 변화, 변경하지 않기로 한 영역, 경고·렌더 상태를 확인한다. 실행 실패·재렌더 실패는 각각 표시한다. 서버 저장 전에는 라이브 변경이며, 저장 후에만 새 불변 버전을 확정한다.

초기 연산은 기존 네 개 허용 명령을 기준으로 늘린다. `document.inspect`, 텍스트 교체, 이동·크기, 이미지 교체 등은 **구현 및 보안·호환 테스트 전까지 미지원**이다. 현재 텍스트 상자 삽입의 고정 좌표는 범용 배치 지능이 아니다.

## 5. 에이전트와 데이터 소유

| 모듈 | 입력 | 출력 | 금지할 책임 |
|---|---|---|---|
| 대화 오케스트레이터 | 사용자 메시지, 권한, 컨텍스트 범위, 도구 결과 | 실행 계획, 스트리밍 상태, 버전 묶인 제안 | 모델 출력의 무검증 실행, 다른 프로젝트 접근 |
| sourcePrepAgent | 출처와 불변 원본 | 변환 후보·파생본·hash·변환 기록 | 원본 덮어쓰기, 자동 고위험 크롭 |
| portfolioAgent | 승인된 자료, 목적, 규격, 문서 상태 | 서사·페이지 계획·수정 제안 | 편집기 객체 직접 변경 또는 검토 합격 선언 |
| reviewAgent | 특정 버전과 실제 렌더·기준 | 차단/경고와 독립 검토 결과 | 원본 변경, 자신이 만든 결과의 독립 승인 |
| DesignCraft 어댑터 | capability/읽기/검증된 편집 요청 | 상태·결과·전후 revision·렌더 | 프로젝트 권한 결정, LLM의 임의 파일 경로 실행 |
| API·저장소 | 인증된 사용자와 프로젝트 범위 | 자료·대화·실행·문서 버전 기록 | 소스 원본 변형, 비밀키 브라우저 노출 |

DB 엔터티와 업로드·삭제 정책은 [WEB_DATA_DESIGN.md](../WEB_DATA_DESIGN.md)를 기준으로 확장한다. 추가로 `editor_sessions`, `document_snapshots`, `edit_proposals`, `edit_operations`, `operation_receipts`를 프로젝트·문서·revision·run에 연결한다. `conversations/messages`와 에이전트 호출, 모델 입력 출처, 비용 확인값은 같은 run으로 묶는다. 모든 관계의 프로젝트 일치와 접근 권한을 서버·DB에서 확인한다.

## 6. 배포 및 운영 가정

- 웹 UI/WASM: 정적 호스팅 및 Cloudflare 후보. API와 분리해서 배포하되 브리지 origin과 CSP, 다운로드·업로드 경계를 검증한다.
- 인증/DB: Supabase Auth와 PostgreSQL 후보. 실제 프로젝트 미생성, 로그인 UI만 구현됐으며 서버의 사용자 검증과 격리는 미구현이다.
- 파일: R2 또는 Supabase Storage 후보. 객체는 비공개, 접근은 권한 확인과 범위가 좁고 만료되는 방식으로 설계한다. 실제 선택은 계정·비용·요구사항 확인 후 결정한다.
- 공급자 검토 근거: [Supabase Auth](https://supabase.com/docs/guides/auth), [R2 서명 URL](https://developers.cloudflare.com/r2/api/s3/presigned-urls/), [Cloudflare Python Workers 파일 수명](https://developers.cloudflare.com/workers/languages/python/stdlib/). 이 문서는 특정 공급자의 계약·요금이나 배포를 확정하지 않는다.
- 에이전트: 현재 CLI와 로컬 파일 경로에 의존하므로 격리된 작업 실행 환경이 필요하다. Claude 개인 CLI 구독을 다중 사용자 서비스에 사용할 권리나 운영 적합성은 확인되지 않았다. 공급자별 인증·과금·동시성·자료 정책을 확인하고 합법적으로 구성한다.
- 현재 API, jobs, 저장 경로와 운영 로그는 단일 로컬 환경에 묶여 있다. 인증이나 작업 큐를 구현하기 전 다중 사용자 공개를 하지 않는다.

## 7. 구현 순서와 검증 게이트

1. **실제 읽기 계약:** 능력표 + 선택/페이지/객체 ID + live revision, 사용자가 편집한 직후의 상태와 저장 전 상태를 읽는다. 브리지 외부 origin·허용되지 않은 메시지 차단 테스트.
2. **제안 전용 세로 흐름:** 합성 프로젝트와 실제 문서에서 선택 페이지 읽기 → 대화 → 구조화된 텍스트/배치 제안. 모델에 전달된 텍스트/이미지와 제외 항목을 확인. 수정은 아직 하지 않는다.
3. **단일 안전 수정:** 예를 들어 선택 텍스트 교체 1개. 사용자 승인 → 예상 revision 검사 → 적용 → before/after 비교 → undo/redo와 충돌, 중복 요청, 중간 실패 검증. 미지원 원자성은 오류로 남긴다.
4. **저장·리뷰:** 라이브 revision을 불변 native 버전에 저장 → 실제 PDF 렌더·해시 → 원본 연결 → 새 검토. 저장 실패·렌더 실패·이전 리뷰 무효화와 서버 재시작을 확인한다.
5. **자료·다양한 작업:** 이미지 이동·크기/교체, 도면 보호, 다중 페이지, sourcePrep·portfolio·review 연계를 한 연산씩 capability·음성 사례 및 회귀 테스트와 함께 추가한다.
6. **실제 사용자:** 인증·프로젝트/자료/대화/작업 격리와 내구성 구현, 서로 다른 두 사용자에 대한 접근 차단 및 브라우저→API→저장소→에이전트→편집기 전체 흐름을 검증한다.
7. **디자인 평가:** 권리 확인된 여러 실제 분야의 사례에 대해 독립적인 인간 블라인드 비교를 진행한다. 합성 테스트와 모델 점수만으로 미적 완성을 주장하지 않는다.

## 8. 미결정과 위험

- Supabase 전용 계정, 실제 프로젝트, OAuth 공급자·과금, 저장소 선택은 사용자의 결정과 실제 설정이 필요하다. 기존 네 프로젝트는 모두 필요하므로 변경하거나 삭제하지 않는다.
- 실시간 공동 편집, 자동 적용 기본값, 모델 선택과 데이터 보존 기간은 결정되지 않았다.
- 브라우저 편집기의 동기적 snapshot·원자적 변경·안정 ID·undo 복원과 서버 멱등성은 아직 검증되지 않았다. 이 능력이 없으면 자동 적용이나 성공을 주장할 수 없다.
- 시각적 레이아웃에 대한 모델 인식 및 실제 디자인 품질은 지금 코드에서 입증되지 않았다. 글꼴 대체, 미리보기·PDF 차이와 범위 밖 변경을 별도로 확인한다.

## 9. 현재 실시간 반영 확인 (2026-11-09)

- REPRODUCED: 로컬 브라우저에서 합성 프로젝트 `verified` 시도 `05`의 대화 입력 및 전송을 실행했다. API 작업 `b3f18bcccd64`는 `failed`, `Editor chat runner failed (exit 1)`을 반환했다.
- REPRODUCED: 같은 실행기의 무도구 합성 요청은 Claude 주간 사용 한도 초과를 반환했다. 따라서 이번 실행에서 모델 응답이나 텍스트 삽입은 검증되지 않았다. 계정 상태 조회의 로그인 여부만으로 모델 요청 성공을 보장할 수 없다.
- CODE_INSPECTED: 현재 저장된 PDF 텍스트 기준의 응답과 사용자가 누르는 텍스트 프레임 삽입만 연결돼 있다. 에이전트가 현재 이미지·페이지 배치를 읽거나 자동으로 디자인을 수정하는 양방향 실시간 동기화는 구현되지 않았다.
- 선행 작업: 사용 한도 회복이나 별도의 적법한 모델 실행 경로를 준비한 뒤, 합성 브라우저 요청 → 실제 응답 → 수동 삽입 → 편집기 결과를 다시 검증한다. 다른 공급자는 현재 구현돼 있지 않다.

## 10. 설계 점검 상태

- BMAD spine 기계 검사는 0건이다. 현재 코드, 상위 AD-1~6 및 ADR-0009와 대조했고, 수정 중 경쟁 상태와 재시작 후 중복 적용을 별도 위험으로 반영했다.
- 독립 리뷰어에 의한 검증은 수행하지 않았다. 원자적 편집, 안정 ID, 장애 복구, 권한 분리와 실제 디자인 품질은 구현·실험 전의 설계 가정이다. 따라서 이 문서는 최종 승인본이 아닌 초안이다.
