# 에이전트별 설계 목표 (2026-11-12)

상태: 제안. 구현 증거가 아니다. 논문은 초록과 arXiv 초록 페이지만 읽었고(DOC_REPORTED), 본문과 코드는 아직 읽지 않았다. 논문 수치는 논문이 보고한 값이며 우리 측정값이 아니다.

이전 조사: `project/research/PAPER_NOTES_AUTODESIGN_HARNESS.md`(AutoDesign, 코드 확인), `PAPER_NOTES_HARNESS_DEEPSLIDES_2026-11-05.md`(AI Harness Engineering, DeepSlides, AHE), `AGENT_EDITOR_PAPERS_2026-11-09.md`, ADR-0009. 이 문서는 그 위에 에이전트별 목표를 정리한 것이다.

## 전제

호스트 모델(Claude)이 DESIGN.md를 받아 직접 디자인하는 방식은 강하다. 과거 블라인드 비교에서 호스트 단독(B0)이 약 0.76, 우리 엔진이 약 0.64였다(작은 표본, 평가자 1명 변동 ±0.07). 그래서 호스트의 디자인 판단을 대체하지 않는다. 호스트가 못 하는 것을 붙여서 넘는다.

- 호스트가 하는 것: 이야기 순서, 위계, 디자인 방향, 문구.
- 우리가 붙이는 것: 렌더 결과를 보고 고치는 루프, 결정적 게이트, 원본과 사실 보존, 편집 가능한 산출물, 범위가 제한된 수정, 경험 축적.

근거: AutoDesign(2608.13560)은 학습된 하네스를 붙인 코드 에이전트가 PosterBench에서 78.32점으로 Claude Design보다 7.45점 높았다고 보고한다. 같은 모델에서 하네스만으로 평균 54.99 → 67.39. 모델이 아니라 하네스가 차이를 만든다는 주장이며 우리 방향과 같다.

## 공통 성공 기준

1. 하드 게이트 실패 0건(잘림, 겹침, 원본 변조, 지어낸 사실). 실패한 산출물은 점수와 무관하게 불합격.
2. 같은 자료와 같은 모델에서 B0(호스트 단독)와 쌍대 블라인드 비교. 사람 평가자 기준으로 우리 쪽 선호가 절반을 넘어야 "더 낫다"고 말한다.
3. 모든 변경은 실제 렌더 시트를 보고 판단한다. 평가자 한 명의 점수로 품질을 주장하지 않는다.

## portfolioAgent — 책을 만든다

- 현재: 호스트가 `book-plan.json`을 쓰고 규칙이 배치한다. 호스트는 렌더 결과를 보지 않는다(열린 루프). 수리는 게이트 규칙 기반이다.
- 약점: 계획 단계가 결과 화면을 모르기 때문에 페이지 리듬과 위계 문제를 못 고친다. B0에 지는 주된 원인으로 본다(HYPOTHESIS).
- 설계 목표:
  1. **디자인 계획 먼저.** 책 전체의 디자인 방향(DESIGN.md: 팔레트, 서체, 그리드, 페이지 리듬)을 호스트가 먼저 쓰고, 그다음 `book-plan`을 쓴다. 참고: Design First, Code Later(2605.26451).
  2. **한 번 고치고 한 번 본다.** 페이지 전체를 다시 쓰지 않고 원자 단위 수정마다 렌더 관찰을 돌려준다. 단계별 렌더 피드백(넘침, 겹침, 잘림), 턴별 비평, 제출 시 하드 게이트의 3단. 참고: ReDeck(2609.00194).
  3. **용량을 아는 슬롯.** 글을 쓰기 전에 각 슬롯이 담을 수 있는 글자 수와 이미지 비율을 호스트에 알려 준다. 참고: PosterMELD(2608.02218), 621편에서 인쇄 가능 비율 81.3% 보고.
  4. 호스트는 좌표를 쓰지 않는다는 원칙은 유지한다. 호스트가 고르는 것은 계획 필드와 수정 연산이다.
- 측정: 게이트 통과율, 수리 횟수, B0 대비 쌍대 선호, 책 1권당 비용과 시간.
- 하지 않는 것: 이미지 생성으로 원본 대체, 템플릿 고정.

## reviewAgent — 독립 검수

- 현재: 해시로 묶인 신선한 리뷰와 최종화 게이트. 8항목 루브릭. 평가자는 `claude -p` 하나.
- 약점: 단일 총점은 잡음이 크다. 사람 평가와의 일치가 확인되지 않았다.
- 설계 목표:
  1. **총점 대신 항목별 쌍대 비교.** 타이포, 레이아웃, 색, 위계 등 항목마다 A/B 중 하나를 고른다. 참고: TASTE(2605.20731)는 디자이너 5명 두 집단, 9개 기준이며, 기성 VLM 평가자가 디자이너 다수결과 일치하지 못했다고 보고한다.
  2. **평가자를 믿기 전에 검정한다.** 사람이 매긴 소수의 쌍으로 평가자 일치율을 먼저 재고, 일치가 낮은 항목은 자동 판정에서 뺀다. 참고: AesEval-Bench(2603.01083).
  3. **내용, 공간, 디자인을 따로 채점.** 사실 충실도, 공간 정확성, 디자인 품질을 한 점수로 섞지 않는다. 참고: ReDeck의 DeckQuiz.
  4. 리뷰 결과는 portfolioAgent의 턴별 비평 입력으로 쓰되, 최종 승인 리뷰는 생성에 관여하지 않은 새 리뷰어가 한다.
- 측정: 사람 쌍대 판정과의 일치율(항목별), 반복 실행 간 판정 일관성.
- 하지 않는 것: 평가자 점수 하나로 품질 주장.

## sourcePrepAgent — 자료를 준비한다

- 현재: 여백 정리, 레벨 보정, 배경 제거. 원본 보존과 `derived.json` 이력. 픽셀 처리만 한다.
- 약점: 자료의 의미를 모른다. 대표 컷과 보조 컷, 도면 종류, 해상도 한계가 계획 단계에 전달되지 않는다.
- 설계 목표:
  1. **의미 태그.** 자료마다 종류(사진, 도면, 다이어그램, 화면), 역할 후보(대표, 보조, 과정), 주제 영역(focus), 인쇄 가능한 최대 크기를 manifest에 기록한다. 호스트가 이미지를 보고 제안하고, 사람이 승인한다.
  2. **중복과 유사 컷 묶음.** 같은 대상의 유사 컷을 묶어 계획 단계가 고르게 한다.
  3. 원본 바이트 불변, 모든 변환은 명시적이고 되돌릴 수 있다는 원칙은 유지한다.
- 참고: Beyond Atomic Layouts(2608.26716)는 VLM이 겹친 다층 구성 이해에 약하다고 보고한다. 태그는 사람 승인 전까지 제안으로만 다룬다.
- 측정: 태그 승인율, 계획에서 대표 컷이 실제 hero로 쓰인 비율, 저해상도 확대 게이트 실패 건수.

## 하네스와 편집 대화 — 관찰, 제안, 승인, 적용, 검증

- 현재: `PROTOCOL-HARNESS.md`는 목표 설계다. 편집 대화는 저장된 PDF 텍스트와 제한된 구조만 본다. 이미지 인식과 자율 수정 루프는 없다.
- 설계 목표:
  1. **수정은 열린 코드 생성이 아니라 구조화된 연산.** 바꿀 객체, 적용할 연산, 보존할 상태로 분해한다. 대상 객체를 먼저 확정하고, 제한된 도구 집합만 쓰고, 수정마다 지시 이행과 나머지 보존을 검증하고, 실패하면 되돌린다. 참고: EditPPT(2608.20381), 과제 성공 66.7~74.9%, 보존 97% 이상 보고.
  2. **단계마다 사용자 피드백.** 완성본 뒤가 아니라 개요, 디자인 방향, 페이지 단계마다 승인을 받는다. 참고: ConvDeck(2609.00226).
  3. **절차 기억.** 성공과 실패 실행에서 자연어 절차를 쌓고, 기존 성공을 깨지 않을 때만 반영한다. 참고: Designer-RSI(2609.22086), AutoDesign(2608.13560). 1과 2가 동작한 뒤에 한다.
- 측정: 수정 과제 성공률, 대상 외 객체 보존율, 되돌림 횟수, 사용자 승인까지 걸린 턴 수.

## pascal-agents (별도 저장소)

DiagramAgent와 pptAgent는 `diagram-set/v1`과 `DESIGN.md`로만 연결한다. 이 문서의 목표 대상이 아니다. 사람이 만든 실제 사례를 예시로 쓰는 방식은 RAP(2610.23230)를 참고하되, 권리 확인 전에는 구조만 쓴다.

## 순서

1. reviewAgent 항목별 쌍대 비교와 사람 판정 소표본. 이게 없으면 나머지 개선을 잴 수 없다.
2. portfolioAgent 디자인 계획 먼저 + 단계별 렌더 피드백.
3. 하네스 구조화된 수정 연산.
4. sourcePrepAgent 의미 태그.
5. 절차 기억.

각 항목은 시작 전에 논문 본문을 읽고, 공개 코드는 라이선스 게이트를 거친 뒤 작업 카드로 만든다.
