# Backend structure: why (2026-11-06)

Researched current practice before restructuring (the first version used `sys.path` bootstrapping and a flat `core/`).

| finding | source | decision |
|---|---|---|
| A **uv workspace** is the standard way to keep several Python packages in one repository: root `pyproject.toml` with `[tool.uv.workspace] members`, each member its own `pyproject.toml`, siblings depend on each other with `[tool.uv.sources] x = { workspace = true }`, **one `uv.lock`**, members installed editable, `uv run --package` per member. Use it when the packages are developed together and can share dependency versions (our case); path dependencies only when members need separate environments. | [uv: workspaces](https://docs.astral.sh/uv/concepts/projects/workspaces/) | root `pyproject.toml` (virtual root) with members `backend/packages/*`, `backend/apps/*`, `agents/{portfolioAgent,sourcePrepAgent,reviewAgent}`. `pascal_bootstrap`/`_boot`/`conftest` path hacks deleted. |
| Common layout: reusable libraries under `packages/`, runnable things under `apps/`; one workspace scales to dozens of distributions (Apache Airflow ships 120+ from one repo) and suits teams up to tens of engineers. | [Modern Python monorepo with uv (FOSDEM 2026 write-up)](https://pydevtools.com/blog/fosdem-talk-modern-python-monorepo/), [python-monorepo-template](https://github.com/clintonsteiner/python-monorepo-template), [uv workspace monorepo guide](https://www.kunalganglani.com/blog/python-uv-workspace-monorepo) | `backend/packages/portfolio-core` (library) and `backend/apps/api` (service). |
| A **shared kernel** must stay small and explicit: only what several modules truly share; if removing something breaks one module it does not belong; a module exposes a public API and others import only that; boundaries are enforced by checking imports. | [Shared Kernel pattern in modular monoliths](https://milanjovanovic.tech/blog/shared-kernel-pattern-modular-monolith), [modular monolith architecture](https://singhajit.com/modular-monolith-architecture/), layers-as-import-rules: [Kraken's 28K-file Python monolith](https://www.besthub.dev/articles/how-layered-architecture-keeps-a-28k-file-python-monolith-manageable-dae5e1ccf880) | `portfolio-core` = model, sources, geometry, quality, guardrails, checks, schemas (grouped by responsibility, not by file type); layout/authors/engine/cli stay in the agents. Contracts with **import-linter**: layers `cli > engine > authors > layout > core`; the kernel imports no agent/app; only `gateways/agents.py` reaches the agents. |
| Namespace packages across distributions are legitimate (PEP 420: no `__init__.py` in the shared namespace directory). | Python packaging practice (each distribution contributes `src/portfolio_agent/<sub>`) | `portfolio_agent` is a namespace across `portfolio-core` and the three agents, so ~90 imports kept their names; `portfolio_agent` and `portfolio_agent.engine` must never get an `__init__.py` (architecture test). |
| Inside the service: for a monolith with several domains, **one package per domain** (`router.py`, `schemas.py`, `service.py`, `dependencies.py`, `exceptions.py`), global modules (`config`, `main`, `exceptions`) at the top; a file-type layout (`routers/ schemas/ services/`) fits only small single-purpose services. Routers stay thin and business logic lives in services; use `app.dependency_overrides` for tests; async only for non-blocking I/O (ours are sync routes in the thread pool, long work goes to jobs). | [zhanymkanov/fastapi-best-practices](https://github.com/zhanymkanov/fastapi-best-practices), [RNFS fork: why domain-based](https://github.com/RNFS/fastapi-best-practices), [DEV: hybrid layered layout](https://dev.to/mohammad222pr/structuring-a-fastapi-project-best-practices-53l6) | `pascal_api/{projects,sources,plans,books,reviews,jobs,catalog}/` each with router/schemas/service; `gateways/` for the agent adapter; `storage/` for files and jobs. Checked 2026-11-06 against the sources (the first version was chosen from experience, not documented). |

Changes made: `common/` -> `packages/portfolio-core`; `api/` -> `apps/api`; flat `core/*.py` -> `model/ sources/ quality/ checks/ guardrails/ schemas/ workspace.py`; JSON schemas moved next to the code that validates them; loose `checks/` scripts became modules (`python -m portfolio_agent.core.checks.layout ...`); `paths.py` -> `workspace.py` (finds the workspace by walking up to the `[tool.uv.workspace]` pyproject instead of counting `parents[n]`).

Not done (yet): publishing wheels (agents are installed editable from the repo; `knowledge/`, `backends/`, `examples/` are agent folders, not wheel data); Docker/CI; a Protocol "port" for the gateway (one implementation today).
